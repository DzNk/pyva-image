# Design

## Context

См. [proposal.md](proposal.md). До изменения `runtime_image.bzl` кладёт Debian-пакет JRE вместе с транзитивными зависимостями в слой для каждой архитектуры. `release.sh` проверяет точные кандидаты и повторяет smoke после pull. В актуальной `main` workflow `ci.yml` уже сохраняет обновления Astral и публикует шесть индексов Java 21, включая четыре варианта amd64-v2/v3.

## Goals / Non-Goals

**Goals**

- Получать патчи Java из официального канала Temurin и воспроизводить сборку по сохранённым входам, как для Astral.
- Сохранить контракт Java 21 и собрать Java 25 с обоими Python minor. Выпускать четыре пары из GitHub Actions.

**Non-Goals**

- Java 17, Java 25 для дополнительных CPU-вариантов, смена Debian 13 в базе и изменение корпоративного GitLab Quality Gates.

## Decisions

### Выбирать релиз при обновлении inputs

Добавить `update_java_manifest.py` по образцу Python updater. Для каждой поддерживаемой ветки читать latest stable из официального `adoptium/temurin<major>-binaries`. Проверять GA-тег нужного major, выбирать два HotSpot JRE tarball для glibc Linux и читать опубликованные SHA-256. Привязать имена и URL к одному тегу и отклонять дубли, несовпадение версии и ошибочный SHA-256. Сравнивать версии и build после `+` численно. Отстающий или неполный релиз и изменившийся SHA-256 того же тега требуют явной ошибки. [GitHub Releases API](https://docs.github.com/en/rest/releases/releases#get-the-latest-release)

Атомарно сохранять релиз, оба URL и SHA-256 в одном `java_runtime.json` с записью на major. Небольшое Bazel repository rule читает запись указанного major и архитектуры и скачивает архив через `repository_ctx.download` с закреплённым SHA-256. Проверка smoke читает ожидаемый релиз из того же JSON. Обычная сборка отрабатывает с кэшированными архивами при недоступном API релизов.

### Переупаковать слой JVM, сохранив пути и зависимости

Использовать один Bazel build step со стандартным `tarfile` и закреплённым Python 3.12, чтобы проверить архив и записать OCI-слой без распаковки на диск. Убрать верхний каталог и разместить содержимое в `/usr/lib/jvm/java-<major>-openjdk-<arch>`. Проверить, что пути и ссылки остаются внутри JRE, сохранить внутренние symlinks, права запуска, `release` и лицензии. Нормализовать владельцев и время записей и gzip. Сохранить `/usr/bin/java`, а `JAVA_HOME` и `LD_LIBRARY_PATH` направить к выбранной JVM. `/etc/certs` сохраняет контракт для Python. Debian native layer использует существующую упаковку.

Сначала зафиксировать работу текущего образа на двух архитектурах. Debian JRE dependency tree приносит системные библиотеки и для Python, включая glibc и zlib. При замене JRE выделить нужные системные пакеты из закреплённого Debian snapshot в отдельный явный список. Сверить ELF-интерпретатор, NEEDED-библиотеки и их разрешение в финальном rootfs для CPython, `java` и `libjvm.so`. Для зависимостей, которые JVM подгружает по ходу работы, выполнить JPype/POI в контейнере с отключённой сетью и проверить загрузку дефолтного truststore через Java API. Bazel lock обновляется при миграции системных пакетов. Последующие обновления Temurin меняют Java-манифест и относящийся к нему lock diff, если он возникает.

Оставить явные цели amd64 и arm64. Сборочная цепочка идёт от JSON к скачиванию архива, упаковке слоя и OCI-образу. Переиспользовать существующие OCI правила и команды загрузки. Документировать поддерживаемую команду сборки рядом с инструкцией обновления.

### Добавить Java 25 через те же правила сборки

Сначала довести Java 21 до прохождения всех существующих проверок. Затем добавить pin и слой Java 25 для каждой архитектуры. Для каждого Python minor сохранить существующие Bazel targets Java 21 и добавить семейство `pyva_runtime_<minor>_java25` с такими же platform/load/index/push targets. Java 25 использует только локальные aliases с `java25`, поэтому оба major можно загрузить рядом. Один Python layer на пару minor и архитектуры используется с обеими JVM. Проверить на каждой платформе ELF-загрузчик, native imports, truststore и POI до выпуска.

### Проверять точный runtime в release и Actions

Расширить существующий запуск `java` внутри `smoke_test.sh` общим строгим режимом для release и проверки Java PR. Читать `java.runtime.version` и vendor, сопоставлять версию и build с сохранённым Temurin pin и отдельно проверять числовой порог выбранной ветки. Для 21 это `21.0.13.1`, для 25 — `25.0.5.1`. Учитывать суффикс сборки вроде `-LTS` и отклонять prerelease. Обычный smoke по-прежнему проверяет выбранный major. [Формат Runtime.Version](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/lang/Runtime.Version.html)

`release.sh` и `smoke_test.sh` принимают `--java 21|25` с default 21. Release включает строгий режим до push и для каждого pull по digest. `image_manifest.py` проверяет выбранную пару по OCI identity. Ошибка указывает Python minor, платформу, ожидаемый major, фактическую и минимальную версию и CVE. Maven в промежуточном stage `Dockerfile.poi-smoke` получает JAR. Проверки выполняет JVM финального образа.

### Обновлять pins в существующем GitHub Actions

Расширить существующую фазу refresh в `.github/workflows/ci.yml`, которая запускается ежедневно и через `workflow_dispatch`. Добавить Java-манифест к разрешённым файлам обновления. После регрессионных проверок сохранять изменившиеся pins в одном коммите через действующий fast-forward push из исходного репозитория. Повтор при неизменившихся inputs использует существующий commit. Сборка и публикация получают этот SHA в том же run. [Триггеры GitHub Actions от встроенного токена](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow)

### Публиковать из GitHub Actions

Расширить release матрицу того же workflow. Четыре baseline задачи содержат Python 3.13/3.14 и Java 21/25, четыре существующие задачи сохраняют Java 21 amd64-v2/v3. Для baseline runner строит обе платформы и вызывает штатный `release.sh` с выбранной Java. Независимые задачи могут завершиться в разное время. Успех workflow требует публикации и pull-проверки всех индексов. Повтор с того же commit проверяет совпадение immutable digests и довыпускает недостающие варианты.

Публикация разрешена в исходном репозитории с основной ветки. Использовать текущие переменные `DOCKERHUB_REPOSITORY`, `DOCKERHUB_USERNAME` и secret `DOCKERHUB_TOKEN`. Действующий вызов `release.sh --channel` обновляет канал выбранной пары после проверки immutable index. Summary выводит теги и digests. Java 25 получает собственные каналы и новые immutable tags.

## Risks / Trade-offs

- [Первый архив нового релиза появляется раньше второго] → кандидат ждёт двух архивов одного тега. До этого Actions показывает, какого файла не хватает.
- [Tarball меняет нативные зависимости и встроенное хранилище сертификатов] → проверить обе архитектуры, загрузку `libjvm.so`, native imports, POI и читаемость JVM truststore. Сохранить документированный способ подключать пользовательский Java truststore.
- [Корпоративный Quality Gates может определять Java по метаданным пакета Debian] → сохранить метаданные поставщика `release` и отдельно подтвердить распознавание Temurin в тестовом прогоне корпоративного gate при наличии доступа. GitHub Actions проверяет исполняемый бинарник и предоставляет его версию в логах.

## Migration Plan

1. Перевести существующие четыре платформенных образа на Temurin 21 от `21.0.13.1+2` и включить gate Java 21.
2. Подключить Temurin 25 от `25.0.5.1+2` и проверить все восемь образов. Сверить существующие команды и теги Java 21.
3. Запустить публикацию Actions из проверенного коммита. Сверить четыре immutable tag, четыре index digest и обе платформы каждого. Для отката выбирать проверенный digest с JVM, проходящей действующий порог.
